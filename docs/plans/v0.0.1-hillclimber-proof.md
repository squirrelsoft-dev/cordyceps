# Cordyceps v0.0.1 — The HillClimber Proof

> **One job: prove the self-improvement loop measurably works, on a task hard enough that a single pass fails. Produce one red number on disk, then climb it.**

This is not the cathedral. It is the keystone test. v0.0.1 exists to answer a single falsifiable question before another line of substrate gets built:

**Does iteration (HillClimbing) measurably beat a single pass — on a deterministic, un-gameable metric the agent cannot reach?**

If yes, Cordyceps has a foundation and we proceed. If no, we found out cheaply, on stone #1, instead of after building the whole tower.

---

## Why this and nothing else

Cordyceps is infrastructure: an autonomous, self-improving agent substrate. Every other property the project promises — autonomy, remote control, self-extension, the inbox triage, the smart-home skills — is downstream of one unproven assumption: **that the self-improvement loop in `spore-core` (the `HillClimbing` strategy) actually produces improvement, not the warm glow of an LLM narrating its own progress.**

That assumption is the only load-bearing unknown. So it is the only thing v0.0.1 is allowed to test.

This is the [`spore-core/examples/rust/12-cordyceps`](../../README.md) story automated: a human watched a ReAct loop do the least work possible and marvel at itself, laughed, added `PlanExecute`, and eyeballed "10x better." **The whole project is replacing that eyeball with a number that can't be argued with.** v0.0.1 builds exactly that and nothing more.

## Scope

### In scope
- A minimal TUI/REPL to talk to the agent, via `agent-repl-kit`.
- A `cordyceps` module: a harness architected on `spore-core` (spore-core is the harness *builder*, not the harness — we architect a HillClimbing harness here).
- The HillClimbing loop wired to a real task, a real proposer, and a real **examiner** (scorer) that is structurally separate from the agent.
- One scored task and its hidden test suite.
- A recorded baseline run (the "fail first") and a recorded climb.

### Explicitly cut from v0.0.1 — and why
Cutting these is the point. Each is a real future feature; none is required to answer the one question, and shipping any of them now is scope-creep wearing a v0.0.1 nametag.

| Cut | Why it waits |
|---|---|
| **petri / microVM isolation** (spore-core issue #106; not yet an enum variant) | The proof needs a deterministic scorer, not a sandbox. `WorkspaceScoped` is enough to run the experiment safely. Add isolation at v0.0.2. |
| **OS-managed daemon / always-on service** | You want to watch every move at v0.0.1. Always-on matters only when the agent works unattended. Module + CLI-lifetime for now. |
| **JIT / multi-part prompt loading** | An optimization. Load the whole prompt; measure first, optimize later. |
| **Polished control plane / remote channel** | The README's v1.0 vision. Irrelevant to whether the loop climbs. |

> **The one edge that can't be delegated:** a self-improving system is designed so its operator doesn't buff every rough edge — the system files its own. That works at *runtime*. It does **not** file the bootstrap edge: proving the climber the first time. The system can't smooth the edge that is its own ignition. This is the single rough spot that has to be filed by hand, and it's this document.

## Architecture (v0.0.1)

```
agent-repl-kit (TUI/REPL)
        │
   cordyceps module  ── HillClimbing harness, architected on spore-core
        │
   ┌────┴───────────────────────────────────────────┐
   │  proposer (does the work)   examiner (scores)    │   ← separated powers
   │  gemma 26b / advisor        held-out test suite  │
   └──────────────────────────────────────────────────┘
```

- **Proposer** — the working agent. Runs a `PlanExecute[ReAct, …]` strategy. May consult an advisor (`minimax-m3:cloud`, opus-tier) or Claude Code / Codex for *proposed changes*.
- **Examiner** — the scorer. Holds the tests. **The proposer never writes, sees, or can modify them.** Runs the agent's output against the suite and returns a number.
- **HillClimbing** — `attempt → score → keep iff strictly better → revise → repeat`, with the examiner as the only scoreboard.

## The experiment

### The task
One task with a deterministic, scored test suite, chosen so that **a single `PlanExecute` pass scores below 100%.** Self-improvement shape, to stay true to the thesis: *the agent is asked to do X, lacks capability/tool Y, must build Y, and Y's tests are the score.*

> If a single shot already passes everything, the task proves nothing about *climbing* — it re-proves ReAct/PlanExecute, which `looper` already proved. The task **must** require iteration to fully solve.

### The fitness function (the whole game)
Reward-hacking is defeated structurally, not by asking nicely. We have all watched agents (Claude Code included) edit a test to make it pass instead of fixing the code. Make that impossible by construction:

1. **Separation of powers.** The scoring tests live with the examiner/harness, read-only, **outside the agent's write scope.** The agent gets the task and maybe a few *example* tests for shape — never the scoring tests. It cannot edit what it cannot reach. (This is the SWE-bench / HumanEval hidden-test model.)
2. **Graded, not binary.** Score = `k/N` tests passing ∈ [0, 1], or a continuous metric where the task supports one (latency, % correct on a labeled set). **Binary 0/1 gives the climber no gradient** — it would climb a cliff in the dark and degenerate into random search. Continuous > graded-discrete > binary. Use the most continuous metric the task honestly supports.
3. **Dev / held-out split.** A **dev set** the agent *can* run for feedback while it iterates, and a **held-out set** it *never* sees, which scores the final result. Report the held-out number. **Dev climbs but held-out stays flat ⇒ overfitting / gaming, detected automatically.**
4. **Tamper = auto-zero.** Any attempt to touch the tests, the scorer, or the harness scores that iteration **zero** and is logged as a reward-hack attempt. The attempt is signal.

### The procedure
1. **Fail first (baseline).** Run the task once, single-shot `PlanExecute`. Record the held-out `k/N`. It will be below 1.0. **This red number on disk is the starting point.**
2. **Climb.** Wrap the task in `HillClimbing`. Proposer attempts → examiner scores the dev set → keep iff strictly better → revise → repeat. Validate against the held-out set periodically and at the end.
3. **Read the delta.** Success is not "the agent passed." Success is **the iterated held-out score climbing past the single-shot baseline to threshold.** The delta between one-shot and climbed *is the proof.*

### Model stack
Heterogeneous on purpose — executor ≠ proposer-of-fixes ≠ scorer — so nothing grades its own homework:
- **Executor:** `gemma 26b` (fast), `gemma 31b` if more density is needed.
- **Advisor / fix-proposer:** `minimax-m3:cloud` (opus-4.8-tier, on the Ollama max plan); Claude Code / Codex for analysis of how the climber itself is doing.
- **Scorer:** the test suite. No model. A number.

## Pre-registered failure conditions

Written **before** the run, so no result gets rationalized after the fact. Hitting one is a *successful experiment* — it tells you the truth.

1. **One-shot already scores 100%** → task too easy; proves nothing about climbing. Redo the task.
2. **Iteration never beats one-shot** → HillClimbing adds no value over a single pass. *This is the real "the loop failed" signal.*
3. **Score climbs via reward-hacking** — tamper attempts, hardcoded outputs, or dev-up-while-held-out-flat → the climb is fake; the metric was gameable.
4. **Score oscillates, or an `N+1` worse than `N` gets kept** → the keep-iff-better gate is broken.

---

## Definition of done

v0.0.1 is done when **one of these is true and recorded:**
- The held-out score climbed measurably past the single-shot baseline to a stated threshold — *the loop works,* proceed to v0.0.2; **or**
- A pre-registered failure condition was hit and written down — *the loop needs work,* and we know exactly which part.

Either outcome is a win. The only failure is producing no number — running in circles instead of failing first.

## Open decisions (resolve at build time, don't pre-optimize)
- **Which exact first task?** Needs: self-improvement shape, deterministic suite, single-shot < 100%, small enough to climb this week.
- **Threshold for "climbed enough"** — pick the held-out delta that counts as proof before running.
- **Upstream loop.** Friction found in `spore-core` while building gets reported back to the open-source project with the why — Cordyceps is the first autonomous consumer of the harness, so it's the first to find these edges.
- **microVM sequencing** (spore-core #106) — bolt-on vs. migrate-in. v0.0.2 question, noted not decided.
